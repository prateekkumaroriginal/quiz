Validate before business logic

Turn an untrusted HTTP body into a trusted GetQuestionsInput before reading its fields.

The contract is a gate

Parsing JSON answers one question: is this valid JSON syntax? The result may still be { "banana": true }. Keep it typed as unknown until ArkType checks the fields.

HTTP bodyuntrusted text
→
JSON parserunknown value
→
ArkType contracttyped input or errors

Boundary rule

Business logic starts only after the contract accepts the value.

Build the HTTP handler

The server uses Hono, but Hono is only the transport layer here. ArkType owns the request shape.

app.post("/v1/questions", async (context) => {
  let body: unknown

  try {
    body = await context.req.json()
  } catch {
    return context.json(
      invalidRequest("Request body must be valid JSON"),
      400,
    )
  }

  const input = GetQuestionsInput(body)

  if (input instanceof type.errors) {
    return context.json(invalidRequest(input.summary), 400)
  }

  // input is GetQuestionsInput here
  const questions = questionBank
    .filter((question) => question.category === input.category)
    .slice(0, input.count)

  const output = GetQuestionsOutput({ questions })
  if (output instanceof type.errors) {
    return context.json(internalError(output.summary), 500)
  }

  return context.json(output, 200)
})

The error check narrows input. Below that check, TypeScript knows the fields exist, and ArkType has checked the same fact at runtime.

A type argument is not validation

This tempting version tells TypeScript what to assume. It does not inspect the value.

// Compiles, but does not validate the fields
const input = await context.req.json<GetQuestionsInput>()

// The caller can still send { "banana": true }
questionBank.slice(0, input.count)

The generic type behaves like a promise from the programmer. The ArkType call supplies runtime evidence.

Errors follow a contract too

Clients should not scrape an arbitrary error string. A shared ApiError schema gives the SDK a stable code and message.

export const ApiError = type({
  error: {
    code: "'INVALID_REQUEST' | 'INTERNAL_ERROR'",
    message: "string",
  },
})
// HTTP 400
{
  "error": {
    "code": "INVALID_REQUEST",
    "message": "count must be at least 1"
  }
}

Test through HTTP

app.request() sends a Request through the real Hono route. This catches mistakes in parsing, validation, status codes, and response serialization.

it("rejects valid JSON with missing request fields", async () => {
  const response = await app.request("/v1/questions", {
    method: "POST",
    headers: { "content-type": "application/json" },
    body: JSON.stringify({ banana: true }),
  })

  expect(response.status).toBe(400)
})

Q&A

  1. Why is the parsed request body still typed as unknown?

    Show answer

    JSON parsing checks syntax. It cannot prove that the value has category, count, or valid values for either field.

  2. What is the earliest line where the server may safely use input.count?

    Show answer

    After the input instanceof type.errors branch returns. On the remaining path, ArkType accepted the input and TypeScript narrowed it to GetQuestionsInput.
